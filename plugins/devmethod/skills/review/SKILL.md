# 代码检视

围绕用户指定的代码范围，以项目的技术定位、模块规则、当前契约和实际调用链开展检视。
支持本地工作区、明确的单个或多个提交、连续提交范围，以及已确认基线与候选的分支差异；不要求存在 PR。

## 项目定位与边界

项目定位、模块地图与红线从两个锚点读取（先读再检视）：

- **入口文档**：`AGENTS.md` / `Agent.md` / `CLAUDE.md`（存在哪个读哪个，含其引用的规则文件）。
- **技术参考**：`.agents/agent-docs/ROUTE.md`（按 [project-route.md](references/project-route.md) 规范维护，可选）——
  仓库定位、模块与依据导航、公共契约注意点、验证命令。

ROUTE.md 若声明了代码分层（自研层 / 继承层 / 生成层），检视时区分各层规则：
改到继承层（框架 / 基座 / 依赖包）核对改动是否因底层能力缺失而必要、是否会在升级时产生冲突面，
不把底层既有行为当成项目契约，也不把项目分支写进通用执行路径。
无 ROUTE.md 时以入口文档与实际代码为准，不为检视补造规约。

范围固定、证据核对、问题输出和复查按 [检视流程补充](references/review-workflow.md) 执行。

## 模块规则与规约依据

- 从变更路径定位适用的入口文档规则与模块既有约定；skill / 插件类改动另读目标 skill 自身的格式与纪律要求。
- 从模块入口及"关联模块/范围/不变量"定位 spec。集中规约位于 `.agents/agent-docs/specs/<module>/`；
  项目另有契约真相源（schema / DDL / 协议定义）时以其为准。
  找不到相应规约时记录缺口，使用真实导出与行为测试核实，不虚构模块规范。
- 对每个受影响模块明确：适用规则、spec 的具体文件与条款、代码/测试入口、已知依据缺口。
  跨模块变更同时读取生产方和消费方规则；前后端契约变化两侧都核对。
- spec 表达当前有效契约；design 表达方案及确认依据；feature/bugfix 解释历史决策与证据。
  未确认方案不替代当前契约，历史归档不自动证明当前行为。引用完整文件名和具体条款。
- 遇到代码、spec 和规则不一致，判断是既存文档漂移、本次遗漏同步还是未经确认的契约破坏。
  不以"代码已经这样写了"证明变更合理，也不机械执行已证实过时的接口描述。
  检视时报告冲突和修订建议，交给开发同步，不在只读检视中直接修改候选代码或文档。

## 重点审视差异

检视对象是明确候选相对基线的变化及其影响，不能用候选代码的静态介绍替代差异分析。

1. 固定候选与基线：记录 SHA、工作区差异及范围内未跟踪文件，区分提交范围与实际运行版本。
2. 逐个检查新增、修改、删除、重命名和配置/默认值/依赖变化，理解变化前后的可观察行为。
   重命名或移动也可能改变导出、包资源、注册发现、相对路径及适用规则。
3. 对关键差异建立"基线行为 → 候选行为 → spec/设计依据 → 受影响调用链与消费者 → 验证证据"。
   特别查找漏掉的调用者、旧数据读者、对称清理路径及未更新的测试/文档。
4. 变更新建或明显加重的问题才认定为本次引入；既存问题作为上下文，除非本次改动依赖它。
   有意破坏兼容需有明确决策、迁移或退役安排与验证；既存过渡实现不授权复制新的耦合。
5. 范围较大时按风险与执行路径组织覆盖清单；不能只读核心文件或新增测试就宣称完成全量检视。

## 检视维度

| 维度 | 重点判断 |
|---|---|
| 技术方向与职责 | 各层（自研 / 继承 / 生成）代码是否放在正确层？是否重复实现底层已有能力或反向依赖？ |
| 需求、规约与实现 | 验收目标、模块不变量、已确认设计和实际差异是否一致？是否遗漏约束或擅自改变语义？ |
| 行为与状态 | 正常、边界、无效输入、重入、并发、取消、关闭和恢复是否维持契约？资源是否成对取得与释放？ |
| 公共契约与兼容 | API、事件、表结构、配置及持久化是否兼容？旧数据、旧调用方和下游消费者是否仍能消费？ |
| 契约真相源同步 | 多份必须配套的真相源（双份方言、双目录、代码与文档契约）是否全部同步？漏一份等于没改 |
| 安全与凭据边界 | 凭据是否脱离受控配置（硬编码、明文入库、进入日志/历史）？不可信数据是否触达 `eval`/`exec`/反序列化？ |
| 项目红线 | ROUTE.md / 入口文档列出的红线逐条核对（执行形态、同步纪律、脱敏、打点等，按项目实际） |
| 范围、质量与复用 | 是否夹带无关修改？是否复用既有公共库、既有抽象与已接入依赖？抽象有真实职责与调用者吗？ |
| 文档与交付 | spec、feature/bugfix、入口文档、契约真相源是否按影响同步？说明与代码及验证是否一致？ |

## 决策记录与行为证据的复查

按 [决策归属与替代](../design/references/decision-records.md) 核对已有记录的更新及替代范围，
不能因"没有新增文档"忽略有效续写，也不能用新记录掩盖仍然存在的旧契约/数据义务。
按 [行为证据](../dev/references/behavior-evidence.md) 复查实际模型/用户可见结果、真实入口、独立副作用与相关负向对照，
核对证据对应版本、范围及重验条件；需要时按 [防错模式提炼](../dev/references/defensive-patterns.md) 检查约束依据。
只核对本次影响，不在检视中自动修文档、清理历史或要求全仓回放。

按 [因果流程与资料可信度](../dev/references/context-and-flows.md) 核对历史资料新鲜度、事实与推断、状态权威及跨边界重建链。
结论分别限定盘点、理解、检视和验证范围；未追通的关系与文档漂移明确说明影响，不以资料齐全或符号指纹未变证明行为正确。
本阶段只报告本次相关的资料同步缺口，不自动修改候选文档或启动知识库建设。

## 证据与结论

沿真实入口追踪注册、装配、执行、事件/结果消费与清理；测试应证明可观察契约，
孤立单测不能证明集成可用、构建产物可部署或旧消费者兼容。
按风险运行匹配候选版本的增量检查与相关测试——命令按项目工具链执行（入口文档 / ROUTE.md 列明；
**未约定时先询问用户，不臆造命令**），必要时进行最小复现和同条件基线对照。
区分本次引入、基线已有、环境受限与未执行；CI 证据核对对应 SHA，定向测试通过不覆盖上层失败。

输出 P0–P3、精确位置、触发条件、实际/预期行为、影响、依据及证据，附覆盖范围、未验证项与复查条件。
不要将无来源的风格偏好、理论分层偏好或未验证猜测写成缺陷。
实现问题交给 `dev`，方案缺口交给 `design`；修复后固定新候选，复查原问题及相关回归。

保持待审代码和文档不变；不自动提交、切分支、改写历史、启动多代理或操作远端平台；
提交与 MR/PR 时机由人工决定，提交前检查项归项目入口文档约定，检视只报告缺口。
