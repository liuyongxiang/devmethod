项目图解 · devmethod v0.2.0 · Claude Code 插件

devmethod 是怎么工作的？

一句话：它把「需求澄清 → 设计 → 开发 → 检视 → 转测」这条开发流水线，做成 AI 编程助手必须遵守的制度——用钩子把规则"焊"进每个会话，用路由技能给任务分诊，用四类文档把过程沉淀成可追溯的记忆。任何项目装上即用。

需求澄清→ coding-flow 分诊→ design 设计→ dev 开发→ review 检视→ testing 转测 · 按需→ 交付

构成：1 个 hook（强制注入）· 5 个技能（coding-flow / design / dev / review / testing）· 4 类受管文档（D 设计 / F 实施 / B 故障 / S 契约）· 2 个项目锚点（入口文档 + ROUTE.md）

1

为什么需要它：AI 直接改代码，问题出在哪？

AI 编程助手"裸奔"干活时很能写，但缺三样东西——devmethod 就是为补齐这三样而生的。

痛点一

想改就改，没有章法

你说"加个功能"，它直接动手。该先出方案的改动没出方案，该问你的没问，代码质量和方向全靠运气。

痛点二

一个会话一失忆

上周讨论过的设计、踩过的坑，换一个会话就忘了。没有档案，同一个错误可能反复踩。

痛点三

没人把关，自说自话

自己写完自己说"已完成"。改动影响了哪些旧接口、契约有没有同步，缺一道独立的检视关。

类比把它想成一家医院的制度，而不是某个更聪明的医生。 AI 是一位动手能力很强的新同事；devmethod 则是他入职的医院：分诊台（coding-flow）决定他今天进哪个科室，会诊制度（design）要求大手术先出方案签字，手术规程（dev）规定怎么动刀，术后复核（review）核对有没有伤到别处，出院清单（testing）交代测试怎么验收——而 病历系统（D/F/B/S 文档）把这一切都记下来，下次接着用。 （类比在"谁说了算"这层不成立，见第 5 节。）
2

全景：任务怎么流过五道工序

任何改动代码的任务（新功能、修 bug、重构、补测试）都要先过"分诊台" coding-flow，它读项目资料后判断从哪个阶段接入，之后按流水线走。大改动必须先出设计并经你确认，日常明确修复可以直接进开发。

向下滚动到这里时，会按任务的实际走向逐步点亮流程。
注意两条琥珀色回环：检视发现的问题不是就地放行，而是打回对应阶段重做——流程允许返工，但返工也要过门。
3

怎么起作用：三层机制拆开看

先说清一个词：技能（skill）就是装进插件的一份详细"操作手册"（SKILL.md），AI 被派到哪个阶段，才加载哪本手册——按需取用，不占内存。而让这套制度真正生效的，是下面三层机制。

机制一 · 强制

Hook：规则不靠自觉

每个会话启动时自动把"改代码必经 coding-flow"注入上下文。

机制二 · 分诊

coding-flow：判断走哪条路

读项目资料、判定改动规模，决定是否先设计、从哪接入。

机制三 · 记忆

文档 + 工具链：过程可追溯

四类受管文档记录一切，脚本自动维护索引和署名。

3a. Hook 注入：规则是"焊"进去的，不是"拜托"记住的

很多规则失败在"靠模型自觉"。devmethod 用 Claude Code 的 SessionStart 钩子解决：装上插件后，每次会话启动（包括压缩重建后），宿主都会自动执行 cat rules.md，把强制路由规则放进上下文。

这是"强制"二字的实现方式：规则每次会话重新注入，不依赖 AI 记性，也不需要项目侧做任何配置。

3b. coding-flow 分诊：什么改动必须先设计？

规则只说"必须走流程"，具体走哪条由 coding-flow 判断。它先读项目的两个锚点——入口文档（AGENTS.md / CLAUDE.md）和 ROUTE.md（模块地图、红线、验证命令）——再按下面的判定路由。

关键取舍：小修不强制走全套（避免仪式感拖慢日常），但大改动的"设计确认"这一步不能省——而且进入设计前必须先问过你。

3c. 文档记忆 + 索引工具链：AI 的"长期记忆"落在哪里

AI 的"记性"不可靠，可靠的记忆只有一种形态：写进项目里的文档。devmethod 规定四类受管文档各管一件事，配套 Python 脚本自动维护索引和署名。

分工口诀：D 管开发前的方案，F 管开发后的事实，B 管故障教训，S 管当前契约——历史归历史、现状归现状，索引自动生成，不用人手维护。

3d. 设计（D）生命周期：什么时候"搬"进 archive

D 文档是四类档案里唯一会"搬家"的：目录位置本身就是状态——proposals 是评审区，active 是开发区，archive 是结局区。搬家必须由真实事件触发，不能随手归档；维护方也随之转移：design 阶段管评审，dev 阶段管开发与归档。

archive 只收「有结局」的设计：shipped（交付确认）、abandoned（明确终止）、superseded（被正式替代）；rejected 永远留在 proposals。
两个最容易被忽略的词：「交付确认」——不是"代码写完"或"测试通过"，而是根据真实测试和交付结论由人确认后才标 shipped；「先回 design」——方向变化不能顺手改旧文档，必须新建设计并以 supersedes / superseded-by 双向关联，旧设计才因此归档为 superseded。另外 archived-date 只是归档管理日期，不作为实际交付证据——真实交付事实记录在 F 文档里。
4

走一遍真实任务："给订单系统加个导出对账单功能"

  1. 分诊你说出需求。

    因为 hook 注入的规则，AI 不会直接上手，而是先调 coding-flow，读入口文档和 ROUTE.md，判断改动规模。

  2. 评估命中"大改动"判定，先问你。

    要新增对外 API、还要动持久化——它停下来问："建议先做设计，可以吗？"你同意，进入 design。不同意就按你的指示办。

  3. design方案成形，经你确认。

    比较"同步导出"和"异步任务＋通知"两条路线，推荐异步并写明理由。设计文档（D-20261119_1030-export-orders）落在 designs/proposals/，你确认后状态记为 approved——AI 无权自己填"已批准"。

  4. dev落实方案，同步留档。

    设计移入 designs/active/；实现代码＋行为测试一起推进；接口变化同步写进 specs/（S 契约更新）；实际选了哪条路线、为什么放弃另一条，归档成 F 文档。

  5. review独立检视，发现问题打回。

    对比改动前后的行为差异，发现一个 P1：旧的同步调用方没做兼容。打回 dev 修复；修完只复查这个问题和相关回归——检视保持只读，不改代码。

  6. testing按需整理转测文档。

    你说"要转测"后，testing 技能把"测什么、在哪测、怎么算通过"整理成测试人员可独立执行的文档。它只写文档，不替你跑测试。

  7. 交付汇报实情，决定权在你。

    汇报实际完成范围、测试结果、检视状态、遗留项——各项分开记录，不互相顶替。要不要提交、什么时候合并，由你决定，流程不越权。

这一趟留下来的 D/F/B/S 文档，就是下一个任务、下一个会话、甚至下一位同事的"项目记忆"。

5

边界与常见误区：它不做什么

把这套流程理解成"AI 全自动开发"就错了。它规范的是 AI 怎么干活，不是替你做决定。

常见误解实际情况
"装上后 AI 会自动帮我提交代码、建 PR。"不会。任何提交前都先展示提交计划（位置、消息、范围）并等你确认；提交、推送、建 MR/PR 的时机一律由人决定。
"testing 阶段会执行测试。"不执行。它只把开发交接整理成"测试人员可独立执行、结果可追溯"的转测文档；要不要跑、谁来跑，另按你的授权。
"review 会顺手把发现的问题改掉。"不会。检视保持只读：输出 P0–P3 问题清单（位置、触发条件、证据），实现问题回 dev、方案缺口回 design。
"没写 ROUTE.md 就用不了。"能用。退化为"读入口文档＋实际代码"，但模块词表和红线得逐次口头确认，效率低一些——所以强烈建议写。
"AI 记得上周讨论过的方案。"不靠"脑子"，靠文档。落了档的讨论（D/F/B/S）随时能查；没落档的口头讨论，下个会话就没了。
"AI 可以自己把设计标记为'已批准'。"不能。技能明确禁止自行填写审批结论或评审人；只有你或真实评审者明确确认才算数。
类比边界医院类比在"谁说了算"这一层不再成立：这位"住院医师"（AI）不是主治医生。方向级变化必须回 design 经你确认；方案批准、提交、合并这些"签字"全部握在你手里。制度约束的是 AI，决定权留给人。
